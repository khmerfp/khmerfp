# Isolated financial ledger

Development/test only. No payment integration, public credit endpoint, production activation, blockchain signing or balance migration.

USD amounts are positive BigInt cents, bounded by PostgreSQL BIGINT. USDC has its own disabled asset identity with six decimals. Existing wallet balances are not ledger opening balances.

Customer accounts are credit-normal liabilities. A mock $100 deposit debits treasury cash 10,000 and credits customer cash 10,000. Reserving 3,000 leaves posted 10,000 and available 7,000. Consuming 1,000 debits the customer and credits the destination customer; releasing the remaining 2,000 changes no posted cash.

Use `createLedger({ pool, authorize, enabled: true, environment: 'test' })`. The mandatory trusted backend authorizer receives a separate snapshot of canonical terms (amounts are decimal strings) and must return exactly true for each permitted operation. Caller changes while authorization is pending cannot change the executed terms. Derive actors from authenticated server context, never request JSON. `user:<id>` can only read/reserve/release/cancel their own funds. `system:<capability>` is restricted to trusted internal financial workers; consumption, posting, account creation, reconstruction and reversal need explicit authorization. Anyone holding the shared runtime database credential is trusted infrastructure and can invoke that database capability; it is not an end-user credential.

Supported methods: createAccount, post, balance, reserve, release, cancel, consume, reverse, rebuild and system-only reconcile. Pass amounts as BigInt and IDs as decimal strings or BigInt. Returned monetary amounts and IDs are decimal strings. Retries must reuse exactly the same actor, action, key and canonical terms. Posting business references are independently unique. Reversals are full only and cannot reverse reservation consumption or reversal journals.

Every operation uses a dedicated connection and explicit transaction, deterministic account locks, then reservation locks. Reconstruction takes an exclusive advisory gate against all ledger writers. Normal operations use the shared gate. Do not nest a ledger operation inside another transaction; the package owns its connection and transaction boundary. Application cancellation does not establish whether a commit occurred: retry with the same idempotency key.

## Database privilege boundary

Migration 0009 revokes PUBLIC access to financial tables and functions. Before any future enablement, a migration administrator must configure a separate NOLOGIN non-superuser owner for all seventeen ledger tables (eight financial tables, seven position tables and two protected audit-state tables, including their identity sequences) and eighteen controlled functions. The service login must not own these objects, inherit the owner role, hold superuser/BYPASSRLS/CREATEROLE privileges or have direct table/sequence write access. Keep CREATE on the function's schema restricted to trusted migration administration.

The ledger service checks these privilege restrictions on every connection before executing an operation and rejects migration-owner credentials. Grant the runtime login only schema USAGE and EXECUTE on `public.financial_execute(text,text,text,jsonb)` and `public.financial_reconcile(text)`. No automatic role or credential provisioning is performed by the application. The disposable integration test creates these separate roles, changes object ownership, grants only this function and proves direct writes and owner-role escalation fail. Trigger functions use fixed pg_catalog search paths and qualified financial table names; deferred audit reads execute as the restricted owner at commit.

Posted history is immutable, journals must be posted/balanced at commit, accounts and assets are immutable, and projections are checked against journal/event history. A database superuser or object owner capable of disabling triggers remains a trusted administrative boundary; these controls do not defend against a malicious database administrator.

## Local validation

- `npm test --workspace @khmerfp/ledger`: unit tests; PostgreSQL test explicitly skips without its dedicated runner.
- `npm run test:postgres --workspace @khmerfp/ledger`: creates a fresh labelled PostgreSQL 16 container, loopback-only dynamic port and tmpfs data; applies all thirteen migrations, runs real integration tests and removes only its own container.
- `npm run lint --workspace @khmerfp/ledger`
- `npm run db:validate-baseline --workspace @khmerfp/db`

No existing or hosted database URL is used by the PostgreSQL runner. Docker Desktop must be available. Use Node.js 22. The tests create mock users and funds only inside that disposable database.

Migration 0010 replaces repeated global commit-time scans with a protected `financial_audit_targets` table. Source triggers enqueue one target per transaction/object; one deferred constraint check validates each final affected journal/account/reservation/operation before deleting its marker. Runtime cannot read, insert, update, delete or truncate markers. No caller-controlled GUC, advisory-lock marker or temporary table is trusted for skipping audits. Original history remains immutable. Account checks still reconcile that account's indexed history, so a very active account can require progressively more work. `reconcile` retains independent full-history validation under the exclusive writer gate. `rebuild` reconstructs projections and is followed by the same commit-time guarantees. Load testing, operational role provisioning and independent review remain required before production. The package has no production wiring. No fractional shares, fees or currency conversion are implemented.

Run `npm run benchmark --workspace @khmerfp/ledger` for bounded real-operation workloads and complete reconciliation after every phase. Synthetic benchmark reports are written to the OS temporary directory, never a production data store. The 10,000-posting acceptance check counts the combined 1,000 and subsequent 9,000 phase durations against 180 seconds; this is a local development threshold only.


## Position accounting and atomic settlement

Migration 0011 adds seven tables: position accounts, journals, entries, balance projections, reservations, reservation events and cash/position settlement links. Existing migrations 0000?0010 and customer wallet balances are untouched. The audit-target kind check is extended; target-state permissions and per-transaction deduplication stay in place.

Use `createPositionLedger` with the same restricted pool and trusted authorizer. Methods are `createAccount`, `balance`, `post`, `transfer`, `reserve`, `consume`, `release`, `cancel`, `reverse`, `rebuild`, `reconcile` and `settle`. Quantities must be positive BigInts divisible by `1000000n`: one share uses one million base units. Only registered CTF tokens with six-decimal ERC20 collateral are supported. Registry token IDs remain NUMERIC(78,0); account foreign keys reference their internal BIGINT IDs. Token registration and PREPARED status do not establish custody, backing or chain finality.

CUSTOMER accounts belong to one user/token. UNALLOCATED inventory can be transferred to customers by authorized internal operations. EXTERNAL_CONTROL is a nonspendable balancing account: its API available balance is always zero. There is no runtime inventory recognition operation. Mock recognition is performed only by the disposable test fixture using migration-owner SQL. Live inventory recognition and chain reconciliation remain future work.

`settle(systemActor, key, terms)` requires buyer/seller cash and position account IDs, both reservation IDs and their immutable `cashReservationReference`/`positionReservationReference`, marketId, tokenId, quantity, priceCents and matchReference. Price is a positive BigInt USD cents per whole share. For example, 2 shares (`2000000n`) at `60n` cents costs exactly 120 cents. Buyers receive 2 shares and sellers receive 120 cents; neither aggregate cash nor token quantities increase. No fractional-cent calculation, fees or USD/USDC conversion is supported.

Settlement uses one connection, one operation and one commit. Lock order is maintenance gate, operation key, market, ascending cash accounts, ascending position accounts, cash reservation, position reservation. It validates ownership, different buyer/seller, exact token/market identity, remaining reservations, active/open/unresolved market and cutoff. It consumes both holds, posts two balanced journals and writes both events plus the immutable settlement link. Deferred checks reject incomplete links, independent unbalanced journals, inconsistent projections and markets closed before commit. Reconciliation checks historical links without requiring a historical market to remain open. Settlement and reservation-consumption journals cannot be reversed independently.

Customer actors may transfer their own available positions and read/reserve/release/cancel their own positions. Account creation, posting, consumption, reversal, rebuilding, reconciliation and settlement require trusted system authorization. No public endpoints or production imports are added. Possession of the runtime credential remains a trusted infrastructure capability; never expose it to users.

The NOLOGIN function owner also needs SELECT on ctf_position_tokens, chain_assets, ctf_conditions, market_outcomes, market_questions and markets. `UPDATE(id)` on markets permits the PostgreSQL row-sharing lock used by settlement; runtime receives neither this privilege nor table writes. Own the new `financial_cash_execute`, `position_execute`, `position_guard` and `position_validate` functions with that restricted owner. Helpers have no PUBLIC/runtime EXECUTE grant. Migration credentials, broad table writes, unsafe definers and membership in any controlled function owner role are rejected by the application service. These operational grants are demonstrated only in disposable tests and are not automatically applied to an existing database.

The required PostgreSQL suite now includes position and atomic-settlement scenarios, forced failures in both journal legs, concurrency, history tampering and reconstruction. It reports a small local reservation/settlement benchmark with latency, sampled lock waits, deadlocks and full cash/position reconciliation. This is not a production capacity claim. The standalone cash benchmark uses the same extended role boundary. CI uses PostgreSQL 16 and rejects skipped required database tests.

Settlement business references are part of the actor-authorized canonical request and are compared to both holds, including during deferred integrity validation. A trusted future order service must authorize those references against the intended orders; this package does not implement an order registry or matching engine. Changing a reservation ID without its approved reference is rejected.


For the larger local position workloads, run `node packages/ledger/test/runPostgres.js --benchmark-positions` from the repository root with Node.js 22 and Docker available. This creates a fresh disposable target, runs the required security suite, measures 1,000 settlements, attempts the remaining 9,000 within a separate 600-second budget, and measures independent/shared-account and mixed workloads. Full reconciliation follows each workload. Latencies include application/database overhead; the report distinguishes pre-reserved settlement calls from reserve/release workflows. The opt-in workload is not run in ordinary CI and writes no benchmark data into the repository.


## Incremental commit validation (0012)

Migration 0012 first takes the exclusive financial maintenance gate and checks complete cash and position history. Inconsistent pre-existing state aborts adoption; it is never silently repaired. Migrations 0000?0011 remain immutable. Populated disposable adoption tests cover open/closed reservations, historical partial fills, completed settlements, subsequent reconstruction and new fills.

A protected `financial_audit_deltas` context captures each locked pre-mutation account or reservation baseline. Immutable new entries independently contribute posted deltas; new reservation events contribute reserved/consumed/released deltas and their actual event IDs. At commit, final projections and counters must match baseline plus independently accumulated changes. Every new journal and settlement link retains its independent strict validation. Normal commits do not scan past reservation consumptions. Full-history `reconcile` remains separate and unchanged; controlled rebuilds use the exclusive gate and full-history checks rather than trusting a damaged projection.

A target's generation points to its protected context. Deferred validation reads the current context, not the original trigger tuple. Successful checks remove both records; later mutations capture another generation. Savepoint rollback restores context changes with the source records. A deferred context-link check rejects orphan state. Direct updates, replacement, deletion and truncation are denied; runtime has neither table writes nor private-helper execution. Restricted NOLOGIN ownership must cover the new table and all six incremental helpers plus the context-link checker; the service verifies every controlled owner and table privilege. The migration itself does not provision production roles or enable custody.

`test:postgres` now requires populated/invalid adoption tests as well as the full cash/position suite, including 2,000 fills on one reservation pair. Required database tests fail on any skip. `--benchmark-positions` measures comparable unprofiled acceptance timings, commit time, p50/p95/p99, growth windows and lock waits. Add `--benchmark-profile` for PostgreSQL function self-time and audit-state measurements; report this instrumentation separately from acceptance timing. Each workload still performs full cash/position reconciliation. No public endpoints, real inventory recognition, payment integration or production activation are included.

Forcing immediate constraints before a multi-step journal or reservation operation is complete can reject that operation. It must never bypass checks. The tests cover completed-prefix validation, deferred rescheduling, savepoint rollback and subsequent generations; normal API transactions use the migration-defined deferred mode.
