# Isolated financial ledger

Development/test only. No payment integration, public credit endpoint, production activation, blockchain signing or balance migration.

USD amounts are positive BigInt cents, bounded by PostgreSQL BIGINT. USDC has its own disabled asset identity with six decimals. Existing wallet balances are not ledger opening balances.

Customer accounts are credit-normal liabilities. A mock $100 deposit debits treasury cash 10,000 and credits customer cash 10,000. Reserving 3,000 leaves posted 10,000 and available 7,000. Consuming 1,000 debits the customer and credits the destination customer; releasing the remaining 2,000 changes no posted cash.

Use `createLedger({ pool, authorize, enabled: true, environment: 'test' })`. The mandatory trusted backend authorizer receives a separate snapshot of canonical terms (amounts are decimal strings) and must return exactly true for each permitted operation. Caller changes while authorization is pending cannot change the executed terms. Derive actors from authenticated server context, never request JSON. `user:<id>` can only read/reserve/release/cancel their own funds. `system:<capability>` is restricted to trusted internal financial workers; consumption, posting, account creation, reconstruction and reversal need explicit authorization. Anyone holding the shared runtime database credential is trusted infrastructure and can invoke that database capability; it is not an end-user credential.

Supported methods: createAccount, post, balance, reserve, release, cancel, consume, reverse, rebuild and system-only reconcile. Pass amounts as BigInt and IDs as decimal strings or BigInt. Returned monetary amounts and IDs are decimal strings. Retries must reuse exactly the same actor, action, key and canonical terms. Posting business references are independently unique. Reversals are full only and cannot reverse reservation consumption or reversal journals.

Every operation uses a dedicated connection and explicit transaction, deterministic account locks, then reservation locks. Reconstruction takes an exclusive advisory gate against all ledger writers. Normal operations use the shared gate. Do not nest a ledger operation inside another transaction; the package owns its connection and transaction boundary. Application cancellation does not establish whether a commit occurred: retry with the same idempotency key.

## Database privilege boundary

Migration 0009 revokes PUBLIC access to financial tables and functions. Before any future enablement, a migration administrator must configure a separate NOLOGIN non-superuser owner for all seventeen ledger tables (eight financial tables, seven position tables and two protected audit-state tables, including their identity sequences) and eighteen controlled functions. The service login must not own these objects, inherit the owner role, hold superuser/BYPASSRLS/CREATEROLE privileges or have direct table/sequence write access. Keep CREATE on the function's schema restricted to trusted migration administration.

The ledger service checks these privilege restrictions on every connection before executing an operation and rejects migration-owner credentials. Grant the runtime login only schema USAGE and EXECUTE on `public.financial_execute(text,text,text,jsonb)` and `public.financial_reconcile(text)`. No automatic role or credential provisioning is performed by the application. The disposable integration test creates these separate roles, changes object ownership, grants only this function and proves direct writes and owner-role escalation fail. Trigger functions use fixed pg_catalog search paths and qualified financial table names; deferred audit reads execute as the restricted owner at commit.

Posted history is immutable, journals must be posted/balanced at commit, accounts and assets are immutable, and projections are checked against journal/event history. A database superuser or object owner capable of disabling triggers remains a trusted administrative boundary; these controls do not defend against a malicious database administrator.

## Position accounting and atomic settlement

Migration 0011 adds seven tables: position accounts, journals, entries, balance projections, reservations, reservation events and cash/position settlement links. Existing migrations 0000?0010 and customer wallet balances are untouched. The audit-target kind check is extended; target-state permissions and per-transaction deduplication stay in place.

Use `createPositionLedger` with the same restricted pool and trusted authorizer. Methods are `createAccount`, `balance`, `post`, `transfer`, `reserve`, `consume`, `release`, `cancel`, `reverse`, `rebuild`, `reconcile` and `settle`. Quantities must be positive BigInts divisible by `1000000n`: one share uses one million base units. Only registered CTF tokens with six-decimal ERC20 collateral are supported. Registry token IDs remain NUMERIC(78,0); account foreign keys reference their internal BIGINT IDs. Token registration and PREPARED status do not establish custody, backing or chain finality.

CUSTOMER accounts belong to one user/token. UNALLOCATED inventory can be transferred to customers by authorized internal operations. EXTERNAL_CONTROL is a nonspendable balancing account: its API available balance is always zero. There is no runtime inventory recognition operation. Mock recognition is performed only by the disposable test fixture using migration-owner SQL. Live inventory recognition and chain reconciliation remain future work.

`settle(systemActor, key, terms)` requires buyer/seller cash and position account IDs, both reservation IDs and their immutable `cashReservationReference`/`positionReservationReference`, marketId, tokenId, quantity, priceCents and matchReference. Price is a positive BigInt USD cents per whole share. For example, 2 shares (`2000000n`) at `60n` cents costs exactly 120 cents. Buyers receive 2 shares and sellers receive 120 cents; neither aggregate cash nor token quantities increase. No fractional-cent calculation, fees or USD/USDC conversion is supported.

Settlement uses one connection, one operation and one commit. Lock order is maintenance gate, operation key, market, ascending cash accounts, ascending position accounts, cash reservation, position reservation. It validates ownership, different buyer/seller, exact token/market identity, remaining reservations, active/open/unresolved market and cutoff. It consumes both holds, posts two balanced journals and writes both events plus the immutable settlement link. Deferred checks reject incomplete links, independent unbalanced journals, inconsistent projections and markets closed before commit. Reconciliation checks historical links without requiring a historical market to remain open. Settlement and reservation-consumption journals cannot be reversed independently.

Customer actors may transfer their own available positions and read/reserve/release/cancel their own positions. Account creation, posting, consumption, reversal, rebuilding, reconciliation and settlement require trusted system authorization. No public endpoints or production imports are added. Possession of the runtime credential remains a trusted infrastructure capability; never expose it to users.

The NOLOGIN function owner also needs SELECT on ctf_position_tokens, chain_assets, ctf_conditions, market_outcomes, market_questions and markets. `UPDATE(id)` on markets permits the PostgreSQL row-sharing lock used by settlement; runtime receives neither this privilege nor table writes. Own the new `financial_cash_execute`, `position_execute`, `position_guard` and `position_validate` functions with that restricted owner. Helpers have no PUBLIC/runtime EXECUTE grant. Migration credentials, broad table writes, unsafe definers and membership in any controlled function owner role are rejected by the application service. These operational grants are demonstrated only in disposable tests and are not automatically applied to an existing database.

The required PostgreSQL suite now includes position and atomic-settlement scenarios, forced failures in both journal legs, concurrency, history tampering and reconstruction. It reports a small local reservation/settlement benchmark with latency, sampled lock waits, deadlocks and full cash/position reconciliation. This is not a production capacity claim. The standalone cash benchmark uses the same extended role boundary. CI uses PostgreSQL 16 and rejects skipped required database tests.

Settlement business references are part of the actor-authorized canonical request and are compared to both holds, including during deferred integrity validation. A trusted future order service must authorize those references against the intended orders; this package does not implement an order registry or matching engine. Changing a reservation ID without its approved reference is rejected.


For the larger local position workloads, run `node packages/ledger/test/runPostgres.js --benchmark-positions` from the repository root with Node.js 22 and Docker available. This creates a fresh disposable target, runs the required security suite, measures 1,000 settlements, attempts the remaining 9,000 within a separate 600-second budget, and measures independent/shared-account and mixed workloads. Full reconciliation follows each workload. Latencies include application/database overhead; the report distinguishes pre-reserved settlement calls from reserve/release workflows. The opt-in workload is not run in ordinary CI and writes no benchmark data into the repository.


## Incremental commit validation (0012)

Migration 0012 first takes the exclusive financial maintenance gate and checks complete cash and position history. Inconsistent pre-existing state aborts adoption; it is never silently repaired. Migrations 0000?0011 remain immutable. Populated disposable adoption tests cover open/closed reservations, historical partial fills, completed settlements, subsequent reconstruction and new fills.

A protected `financial_audit_deltas` context captures each locked pre-mutation account or reservation baseline. Immutable new entries independently contribute posted deltas; new reservation events contribute reserved/consumed/released deltas and their actual event IDs. At commit, final projections and counters must match baseline plus independently accumulated changes. Every new journal and settlement link retains its independent strict validation. Normal commits do not scan past reservation consumptions. Full-history `reconcile` remains separate and unchanged; controlled rebuilds use the exclusive gate and full-history checks rather than trusting a damaged projection.

A target's generation points to its protected context. Deferred validation reads the current context, not the original trigger tuple. Successful checks remove both records; later mutations capture another generation. Savepoint rollback restores context changes with the source records. A deferred context-link check rejects orphan state. Direct updates, replacement, deletion and truncation are denied; runtime has neither table writes nor private-helper execution. Restricted NOLOGIN ownership must cover the new table and all six incremental helpers plus the context-link checker; the service verifies every controlled owner and table privilege. The migration itself does not provision production roles or enable custody.

`test:postgres` now requires populated/invalid adoption tests as well as the full cash/position suite, including 2,000 fills on one reservation pair. Required database tests fail on any skip. `--benchmark-positions` measures comparable unprofiled acceptance timings, commit time, p50/p95/p99, growth windows and lock waits. Add `--benchmark-profile` for PostgreSQL function self-time and audit-state measurements; report this instrumentation separately from acceptance timing. Each workload still performs full cash/position reconciliation. No public endpoints, real inventory recognition, payment integration or production activation are included.

Forcing immediate constraints before a multi-step journal or reservation operation is complete can reject that operation. It must never bypass checks. The tests cover completed-prefix validation, deferred rescheduling, savepoint rollback and subsequent generations; normal API transactions use the migration-defined deferred mode.


## Reading the SQL implementation

The immutable migrations are executable history. Do not reformat or reorder them: both artifact validation and Drizzle history depend on their bytes. Formatted **reading copies only** are available in `packages/db/sql-reference/`, outside the migration runner directory. Never execute that directory or point Drizzle at it. Each copy identifies its executable source; `manifest.json` pins both hashes and the formatter revision. The archived challenge proposal also has a labelled reading copy and remains outside the migration chain.

Start with these copies:

1. [0009 cash foundation](../db/sql-reference/0009_financial_ledger.sql): tables, cash guards, immutable journals and initial operations.
2. [0010 targeted audits](../db/sql-reference/0010_targeted_financial_audits.sql): deduplicated deferred checks and full reconciliation.
3. [0011 positions and settlement](../db/sql-reference/0011_position_accounting.sql): share inventory, reservations and the atomic `SETTLE` branch.
4. [0012 incremental validation](../db/sql-reference/0012_incremental_financial_validation.sql): locked baselines, authoritative entry/event deltas and mandatory commit checks.

Tables, keys and indexes define structure. Guards and posting functions implement business rules; deferred constraint triggers verify invariants before commit. The JavaScript service authorizes canonical terms, acquires one connection, begins a transaction, calls `financial_execute`, commits after validation, and rolls back on failure. `financial_execute` dispatches cash actions to `financial_cash_execute` and position/settlement actions to `position_execute`. Later migrations replace earlier function definitions, so read the chain in order rather than treating an earlier copy as the current standalone implementation.

For a settlement, SQL locks cash accounts before position accounts, validates market/cutoff and both business-bound reservations, creates the cash and share journals, consumes the reservations, records their settlement link, and runs independent commit-time checks. Every leg succeeds together or the transaction rolls back. This is internal database accounting, not a blockchain submission. Reconciliation and controlled projection reconstruction remain separate operations.

The copies use labelled sections for tables, indexes, constraints, functions, triggers and permissions **in their original execution order**. Sections may repeat because backfills, validation, grants and triggers have dependencies; grouping by moving statements would be unsafe. Existing runtime SQL is formatted in its owning service/model/initialization file; short queries and dynamic fragments remain where moving them would hide the transaction context. Validator expectations and test fixtures remain authoritative and are not rewritten to match a new representation.

Check the copies with `node packages/db/scripts/sqlReadability.js` and `node --test packages/db/scripts/sqlReadability.test.js` from the repository root. The check compares pinned canonical LF hashes and ordered SQL tokens, recursively including PL/pgSQL bodies. Only layout, comments and unquoted case are ignored; quoted strings/identifiers, operators, parameters and statement boundaries remain significant. This complements actual disposable PostgreSQL tests and does not replace semantic/security review. Regenerate and review copies after a new approved migration; never update historical source hashes merely to make a reading copy pass.

To regenerate the copies, use the reviewed pgFormatter revision in the manifest: `node packages/db/scripts/buildSqlReadingCopies.js --formatter /path/to/pgFormatter/pg_format`. On Windows, add `--perl "C:/Program Files/Git/usr/bin/perl.exe"` when Perl is not on PATH. The builder verifies the formatter revision and token equivalence before writing any reading copy; it never writes source migrations, proposals or metadata. Review the resulting reference diff, then rerun both reading-copy checks. CI verifies the reference inventory and rejects stale or modified source/copy pairs.


## Generalized registry compatibility (0013, local)

The new registry separates atomic outcomes, exact observation terms and display claims. `market_observation_specs` stores a reference asset, measurement unit, decimal scale, domain and source/timezone policy; it stores no live or executable price. `market_outcome_tokens` maps YES/NO for a selected outcome to the canonical token. Binary aliases share inventory. Composite NO tokens have no atomic-outcome anchor.

Only the token-to-market joins in `position_execute` and `position_validate` change: both now follow token ? condition ? question ? market. A unit test compares all accounting SQL tokens with the original functions after that exact join substitution. Reservations, whole-share precision, USD cents, privilege boundaries, idempotency, posting, audit deltas and reversal restrictions remain unchanged. All original migration files remain immutable.

Recurring markets use distinct immutable market/question/condition identities; optional series/round keys prevent duplicate round identifiers. No recurring orchestration, market orders, fees, payment integration, inventory creation, frontend activation or contract change is implemented. At the Phase 4.3 checkpoint, categorical and price-range accounting was blocked at database write boundaries. Migration 0014 introduces the restricted mock-only path described below. Live chain verification and redemption remain separate work.


Phase 4.4 generalized mock accounting reuses the same journals, reservations and atomic settlement. Migration 0014 retains the five database write guards and replaces the temporary rejection with immutable, migration-owner-provisioned token verification evidence. Only testnet, six-decimal ERC20 collateral, matching deployment/condition identities and registered canonical claim mappings qualify. Evidence has only `MOCK_ONLY` scope; it proves neither real inventory backing nor on-chain finality. Historical binary eligibility is preserved. Runtime roles receive no enrollment or evidence-mutation permission. Whole shares and integer USD cents remain separate from reference-price observation precision. No orders, matching, payments, live recognition or production activation are included.

The pure `src/tokenVerification.js` helper derives condition, collection and position IDs before preparing mock evidence. ## Persistent trading foundation (0015, local only)

`createTradingService` reuses the existing transaction client and trusted authorizer. It exposes only place, cancel, expire, controlled fill, command recovery and reconciliation operations. The backend authorizer must validate the current KhmerFP session, user verification and action capability; the database actor string alone is not authentication. There is no public manual-fill endpoint, frontend integration or automatic matching loop. The constructor is disabled by default and refuses production/staging.

- `trading_books`: one canonical token and immutable market/round identity per book. Binary display aliases share that book; categorical singleton/complement tokens do not.
- `trading_commands`: actor-bound idempotency terms, persistent per-book sequence and the immutable original command receipt. Recovery returns that receipt, not a fresh order-status snapshot.
- `trading_orders`: owner, BUY/SELL, whole-share quantity, 1-99-cent limit, account links, reservation links and generated remaining quantity.
- `trading_fills`: immutable selected counterparties, execution price/quantity and exactly one internal accounting settlement.
- `trading_order_events`: immutable command/order events with deterministic per-command ordinals.
- `trading_outbox`: one durable identity per event, written in the same transaction. No publisher or delivery acknowledgment is activated.

Order states are PENDING, OPEN, PARTIAL, FILLED, CANCELLED, EXPIRED and REJECTED. PENDING exists only during synchronous acceptance and cannot commit. A valid owned order with insufficient cash or inventory becomes REJECTED with no reservation; malformed, unauthorized or closed-market requests roll back. Commands move from PENDING to APPLIED in the same transaction. Terminal orders cannot reopen. GTC ends at the immutable market cutoff; expiry is an explicit system operation, not a recurring scheduler.

Lock order is maintenance gate, market, canonical book/command, ascending order IDs, ascending cash accounts, ascending position accounts, then reservations. SQL composes existing `financial_execute` calls on the same PostgreSQL transaction; it never calls independently committing JavaScript ledger methods. A fill consumes the correct order holds, transfers cash and the exact position token, releases BUY price improvement, updates quantities and writes the fill/events/outbox. Deferred checks independently verify order-to-reservation and fill-to-settlement relationships. Releasing an order hold through the ordinary ledger service without changing its order is rejected at commit.

The future Phase 4.6 engine will choose counterparties and enforce price-time selection and maker-price policy. This boundary only validates a supplied pair and an execution price within both limits. It does not combine complementary books, create synthetic inventory or perform CTF mint/merge. A successful fill is explicitly INTERNAL_LEDGER accounting, not completed blockchain settlement. The existing exchange contract remains binary-only.

An uncertain COMMIT network response raises an UNKNOWN outcome; retry/recover with the same actor, operation key and exact terms. A database-reported commit rejection is ROLLED_BACK. Never submit a replacement operation key merely because the response was lost. Runtime roles need only reviewed entry-point execution grants; trading tables and private helpers must remain owned by a separate restricted NOLOGIN role. No raw SQL or eligibility enrollment is exposed.

Run `node packages/ledger/test/runPostgres.js` under Node 22 for the required disposable PostgreSQL suite. Tests cover mock binary/categorical/range orders, atomic fills, idempotency, rollback, expiry, durable visibility and reconciliation. Local benchmark samples are not production capacity evidence; the Phase 4.4 shared-account performance limitation remains open.

The older `server/src/demo/orderService.js` remains a separate local-Hardhat demonstration with file-backed, wallet-signed orders. It is not an equivalent PostgreSQL order table. No demo orders, signed payloads or legacy balances are imported into this custodial foundation. Future authenticated order routes must adapt the canonical registry and trusted session policy explicitly.

Acceptance is checked again after acquiring the book lock and at commit. A request that waits past the cutoff cannot leave a new committed hold. Recovery of an already committed receipt is still allowed after cutoff, and cancellation/expiry remain separate authorized exits.


### Phase 4.6: automatic direct-token limit matching (checkpointed locally)

Migration 0016 adds `matching_markets` and `matching_requests`. The market-wide sequence is the durable queue across all canonical token books in that market. Accepted PLACE commands reserve funds immediately, but their orders cannot act as makers until the worker finishes their queue position. CANCEL and EXPIRE requests join that same queue. A queued cancellation receipt does not mean the reservation has already been released.

`createMatchingService` and `runMatchingWorker` are internal opt-in backend components. Supply a restricted pool, a trusted live-session/capability authorizer, a system actor and an AbortSignal. No HTTP endpoint, scheduler or automatic process startup is installed. The service uses one dedicated connection and one transaction per worker step; polling holds no transaction open. Separate processes safely share the same PostgreSQL queue. Independent markets may advance concurrently; a market advisory lock prevents workers or later submissions from overtaking its head command. A paused incoming head is cancelled in sequence, releasing its unused hold without trading.

A step selects the best eligible older resting order of the exact same canonical token: lowest SELL for an incoming BUY, highest BUY for an incoming SELL, then persistent market sequence. It fills the smaller remaining quantity at the resting maker's signed-off database limit price. It calls the existing private settlement primitive, preserving atomic cash/position transfers, price-improvement release, order updates, immutable fills, events and outbox. Runtime access to the renamed primitive is revoked; the public trading boundary rejects FILL requests. Whole shares, 1-99 cent limit orders and zero fees remain the supported scope.

If the next eligible maker is the same user, the incoming remainder is cancelled and its remaining hold released. Earlier fills remain committed, the maker is unchanged, and the cancellation event records SELF_TRADE_PREVENTION. No worse maker is selected around that order. At cutoff, an unfinished incoming remainder expires. There is no general recurring-market or resting-order expiration scheduler yet; explicit sequenced expiry remains available.

Progress and each fill commit together. After a worker crash or uncertain COMMIT, another worker reads the same durable head and step counter. It never guesses a replacement fill or publishes an event before commit. Historical Phase 4.5 orders are adopted as resting without changing holdings; within each historical book their established priority sequence is retained. Books had no prior common market sequence, so adoption uses book ID then the established book sequence as a deterministic historical merge.

This is internal ledger settlement, not on-chain settlement. No payment, wallet, contract, frontend, complementary mint/merge, market-order or fee integration is included. Production custody remains disabled. Performance samples are local smoke measurements, not production capacity guarantees.


Concurrency note: the historical 0015 cross-book benchmark can deadlock when foreign-key KEY SHARE locks are upgraded for cash reservations. Its diagnostic records actual deadlocks rather than claiming zero. Migration 0016 locks the affected cash and position accounts before order insertion, and market sequencing serializes books in the same market. Only confirmed PostgreSQL deadlock rollbacks are retried (at most twice), with the same immutable actor/key/terms and fresh authorization. Unknown commit outcomes are never automatically retried. The automatic matching benchmarks and cross-market shared-cash regression require zero deadlocks. A paused queue is drained in sequence: each unfinished incoming remainder is cancelled with MARKET_PAUSED, preserving past fills and releasing unused holds before advancing to later requests. Broader cancellation recovery remains Phase 4.8 work.


The disposable runner also executes `matchingRecovery.test.js`. Its isolated child process is killed before and after COMMIT, then a new service resumes from PostgreSQL; no duplicate fill is allowed. Test-only credentials travel over process IPC and are never printed. Required CI scenarios fail the runner if absent or skipped. Performance diagnostics call bounded SQL steps immediately; the default worker's 250 ms poll interval and one step per market per poll impose an additional throughput limit. The measurements are not daemon or production capacity claims.

Paused-head checkpoint verification: 168 trading/accounting tests, eight adoption tests and five real process-recovery tests passed with zero skips. Paused BUY/SELL cancellations preserve completed fills and drain in sequence; no bypass queue or settlement permission is introduced.


## Phase 4.7: protected market orders and quotes (local, uncommitted)

Migration 0017 adds only `trading_order_policies`; existing LIMIT/GTC orders have no policy row and retain their behavior. A MARKET/IOC order has an immutable policy and can never become a resting maker. Requested quantity, accounts, exact canonical token and price protection remain immutable order terms. No public HTTP route or frontend integration is enabled.

Use `createTradingService(...).placeMarket(actor, operationKey, terms)`. Terms retain marketId, tokenId, side, quantity, priceCents, cashAccountId and positionAccountId. BUY also requires `maxSpendCents`. Amounts use BigInt, quantities use whole-share base units, and prices remain 1-99 USD cents. For BUY, priceCents is the maximum execution price; for SELL, it is the minimum. SELL must not include a cash cap. BUY caps must be positive and at most requested whole shares times maximum price; a smaller cap explicitly permits partial execution.

BUY reserves exactly the authorized cash cap. The worker computes each fill from remaining quantity, remaining reserved budget and the resting maker price. It does not release per-fill price improvement from a market BUY: that budget may fund additional requested shares at better prices. A full fill releases leftover cash in the same transaction. A partial IOC remains at the durable queue head until its next bounded step cancels the unfilled quantity and releases remaining cash. A fully spent cash reservation may already be consumed; terminal cancellation then changes only the remaining order quantity, without attempting an invalid zero-value reservation release. SELL reserves the requested exact-token quantity, sells at eligible maker prices and releases unused shares when finalized. No fees, fractional shares, synthetic liquidity, minting or merging are added.

Market and limit orders share the same queue, maker selection, self-trade prevention and private accounting settlement primitive. Unfinished IOC requests remain recoverable after partial execution or uncertain commits. Paused heads are cancelled in sequence under the reviewed 0016 policy; cutoff expiry takes priority. Runtime callers cannot invoke the private market-acceptance or fill helper, mutate an IOC policy, remove a policy to turn an IOC into a limit order, or expose an IOC as resting liquidity.

Use `createQuoteService(...).estimate(actor, terms)` for an indicative quote. Inputs are marketId, tokenId, side, quantity, priceCents and a BUY maxSpendCents. No account IDs or quote-authorized spending are accepted. The service uses a read-only repeatable-read transaction; the STABLE SQL function uses committed eligible resting orders for that exact token. Quotes report requested/executable/unfilled quantities, best price, average and worst estimated execution prices, total cents, explicit protection, book version, snapshot ID and generation time. Average price is an exact rational `{ numerator, denominator }`: total cents divided by executed whole shares. Consumers may format it for display without treating a rounded result as an execution instruction.

Quotes do not reserve funds, verify affordability or guarantee future liquidity. They stop at applicable self-trade protection and never derive executable NO prices from YES prices. A stale quote cannot expand submitted quantity, price protection or spending cap; execution always rechecks live committed state. The quote entry point requires a trusted user authorizer and remains production-disabled like the other local services.

Operational role setup must also assign the policy table and its guard/audit functions, the private market acceptance helper and the quote function to the restricted owner. Grant runtime EXECUTE on matching_quote(text,jsonb) only when read-only estimation is intended; do not grant direct policy writes or private helper access. Production custody remains disabled.
